# Описание проекта: Учебник по эмуляции (v2)

---

## 1. Концепция и позиционирование

### 1.1 Трактовка проекта

Это не учебник в узком смысле слова — это **многоуровневая инженерная программа подготовки
системных разработчиков и авторов виртуальных машин / эмуляторов** *(emulator / virtual-machine /
system programmer)*. Мета-проект рассчитан на **10–15 лет** активного развития.

Эмуляторостроение рассматривается не как заучивание алгоритмов, а как **моделирование полного
инженерного цикла**: выбор инструментария → чтение спецификаций → формулирование сомнений →
проектирование архитектуры → написание тестов → отладка → рефакторинг.

### 1.2 Ценность и уникальность

Проект заполняет критический пробел в литературе по эмуляции — между:
- сухой академической теорией,
- тривиальными туториалами в стиле «скопируй `switch-case`».

Сильнейшая педагогическая концепция — **«наставник рядом»**: демонстрация живого хода
инженерной мысли, включая тупики, рефакторинг, ложные решения и альтернативы. Читатель видит
не чистый результат, а **процесс инженерного мышления**.

Проект следует лучшим практикам классической литературы по эмуляции (Emulator 101, Gopher2600)
и педагогической традиции таких авторов, как Паттерсон и Хеннесси, Мальвино, Керниган.

### 1.3 Виртуальный автор и стиль подачи

Личностью и стилем «автора» является **Брайан Керниган** (Brian Kernighan) — Bell Labs,
Princeton University. Это означает:

- живая человеческая подача без академической сухости;
- простота и ясность стиля; объяснение сложного через простое;
- повторение сложных моментов там, где это полезно для понимания;
- простые и понятные аналогии из повседневной жизни;
- лёгкий иронический стиль, уместный небольшой юмор;
- обращение к истории там, где это интересно и поучительно.

## 2. Архитектура курса

### 2.1 Две оси учебника

Весь курс выстроен по двум пересекающимся осям:

| Ось | Описание |
|---|---|
| **Сюжетная / историческая** | Хронологическая лента развития вычислительной техники от ламповых ЭВМ до современных консолей |
| **Учебная / дидактическая** | Лестница концептуальной сложности — каждый следующий шаг вводит строго 1–2 новые архитектурные концепции |

Эти оси **не всегда совпадают**: педагогическая сложность первична. Возраст системы не равен
простоте её реализации. Учебный маршрут следует за педагогической сложностью, а не за датой
выпуска железа.

### 2.2 Три параллельные оси обучения

Каждый модуль курса развивает студента одновременно по трём направлениям:

```
┌─────────────────────────────────────────────────────────────┐
│  1. КОМПЬЮТЕРНАЯ АРХИТЕКТУРА И ЖЕЛЕЗО                        │
│     CPU → память → шины → I/O → прерывания → таймеры →      │
│     DMA → видео → звук → накопители → ROM/прошивки →         │
│     ОС → периферия → тайминги → недокументированное          │
│     поведение → отладка → тестирование → реверс-инжиниринг  │
├─────────────────────────────────────────────────────────────┤
│  2. НИЗКОУРОВНЕВЫЙ GO                                        │
│     двоичное представление → битовые манипуляции →           │
│     моделирование памяти → производительность →              │
│     конкурентность (строго на границах) → профилирование →  │
│     тулинг → инструменты-спутники                           │
├─────────────────────────────────────────────────────────────┤
│  3. ИССЛЕДОВАТЕЛЬСКАЯ ДЕЯТЕЛЬНОСТЬ                           │
│     «Как узнать работу неизвестной системы»:                 │
│     анализ исходников эмуляторов → тест-сьюты →             │
│     тесты на реальном железе → самописные тест-ROM →        │
│     поиск расхождений → реверс-инжиниринг                   │
└─────────────────────────────────────────────────────────────┘
```

### 2.3 Четырёхуровневая классификация модулей

Методологически важно не смешивать процессоры, целые системы и концепции в один список.
Принята следующая классификация:

| Тип | Название | Описание |
|---|---|---|
| **1. Ядра (модули ISA)** | CPU-модуль | Чистая программная модель процессора: регистры, система команд, флаги, прерывания, тайминги |
| **2. Семейства и дельты** | Дельта-глава | Базовый модуль чипа + дельта-главы на модификации (6502 → 65C02 → 65816; 8080 → Z80 → LR35902) |
| **3. Машины** | Системный модуль | Ядро + системная шина + память + видеочип + звук + контроллеры + периферия + форматы носителей |
| **4. Сквозные модули** | Lab / Module | Техники, общие для всех платформ: арбитраж шин, синхронизация по тактам, рендеринг, носители, отладчики |

Дельта-подход экономит объём и учит **видеть эволюцию архитектур**, а не воспринимать каждый
чип как изолированный объект.

### 2.4 Структура прогресса: основная линейка и дополнительные ветки

Курс отказывается от строго линейной цепочки «система → следующая система» в пользу
**древовидной структуры** с 18 основными модулями (М0–М18):

- **Основная линейка (М)** — фундаментальные модули; каждый следующий строго опирается на
  предыдущий; содержит ключевые CPU, системы, сквозные Lab/Module и **встроенные проекты-спутники**.
- **Дополнительная ветка (Д)** — промежуточные модули между основными; вводят 1–2 новые
  концепции; факультативны, но рекомендованы.
- **Lab** — обязательные концептуальные лабораторные модули, стоящие между конкретными модулями М.
- **Module** — обязательные тематические сквозные модули (реверс-инжиниринг, форматы, HLE/LLE и т.д.).

### 2.5 Критика «возраст = простота»

Хронологический возраст системы **не** коррелирует напрямую с простотой эмуляции:

| Система | Почему сложнее, чем кажется |
|---|---|
| Мейнфреймы 1950–60-х (IBM 709/7090) | 36-битные слова, знак-величина (sign-magnitude), 6-битный BCD, независимые каналы I/O, острый дефицит документации |
| Atari 2600 (1977) | Нет кадрового буфера; видео формируется прямо во время хода луча («racing the beam»); эмулятор обязан быть cycle-accurate с первой строки |
| Ранние ЭВМ (ENIAC и др.) | Нестандартная разрядность, десятичная арифметика, редкая документация, нет тест-сьютов |

**Что реально просто для старта:** синхронная шина, стандартные байты кратные степеням двойки,
дискретный фреймбуфер, исчерпывающая документация — CHIP‑8, Space Invaders (Intel 8080), Apple I.

## 3. Язык реализации — Go

### 3.1 Обоснование выбора

Go выбран как основной язык курса по совокупности причин.

**Сильные стороны для задач эмуляции:**
- Типы с фиксированной разрядностью: `uint8`, `uint16`, `uint32`, `uint64`, `int8`… — прямое
  соответствие регистрам и шинам реального железа.
- `math/bits` — аппаратные битовые операции без магии.
- Встроенные тесты (`testing.T`), бенчмарки (`testing.B`), фаззинг (`testing.F`), `pprof`.
- Jump table для больших `switch` начиная с Go 1.19 — производительность диспетчера опкодов.
- Экспорт в WASM: интерактивные эмуляторы прямо в HTML-учебнике (реализуется в М10).
- Идеален для интерпретаторов, шин, отладчиков, CLI-тулинга, тестов вплоть до уровня PS1/GBA.

**Ограничения Go (показываются явно, не замалчиваются):**
- Горутины и каналы **нельзя** использовать для потактовой синхронизации CPU/PPU/APU —
  убьют производительность и детерминизм. Ядро эмулятора строго **однопоточно**.
  Единственное легитимное использование горутин — очередь звукового буфера на границе с ОС.
- Паузы сборщика мусора (GC) вызывают заикания звука и видео. В горячем цикле инструкций
  не должно быть аллокаций памяти (zero-allocation паттерны).
- Отсутствие удобного встроенного JIT-ассемблера ограничивает чистый Go уровнями до PS1/GBA.
  Для PS2 и выше без dynarec играбельной скорости не достичь.

### 3.2 Go как педагогический инструмент

Курс показывает **границы языка** через точечные сравнительные упражнения:
- Где мешает GC и как лечить (zero-allocation, arena-аллокаторы).
- Где горутины полезны (звуковая очередь) vs. где губительны (такт-точная синхронизация).
- Рубеж 3D-систем: сквозной модуль «Когда Go перестаёт хватать» — демонстрация dynarec на C/Rust,
  CGO + mmap, LLVM backend.

### 3.3 Ключевые паттерны кода на Go

```go
// Базовая абстракция шины — общий тип для всех модулей курса
type Bus struct {
    RAM     []byte
    devices []Device
}
func (b *Bus) Read(addr uint16) byte      { ... }
func (b *Bus) Write(addr uint16, val byte) { ... }

// Диспетчер опкодов: switch vs. таблица вызовов — сравниваются явно
var table [256]func(*CPU)   // func-table подход; генерируется go:generate

// Конечный автомат состояния PPU
type PPUState uint8
const (
    StateHBlank PPUState = iota
    StateVBlank
    StateOAMSearch
    StateDrawing
)
```

Разбираются компромиссы: `switch` по опкоду против таблицы `[]func()`, отказ от threaded
dispatch из-за специфики модели памяти Go.

### 3.4 Сквозной унифицированный фреймворк

С первых уроков (М0–М1) развиваются **общие базовые типы**, используемые во всех последующих
модулях без исключения:

```
Bus  ──  CPU  ──  Clock  ──  Device  ──  Debugger  ──  TestHarness
```

Каждый новый эмулятор **наращивает** общую кодовую базу, а не пишется в изолированном стиле.

### 3.5 Встроенные проекты-спутники

Проекты-спутники — **обязательная и неотъемлемая часть учёбы**, встроенная в основную линейку
в наиболее ранней педагогически уместной точке. Они не являются опциональными и не собираются
в конце курса — каждый появляется тогда, когда он уже нужен и может быть осмыслен.

| Спутник | Модуль | Суть |
|---|---|---|
| **Headless-отладчик (старт)** | М0 | Дамп регистров, память (hex+ASCII), трейс инструкций; растёт вместе с курсом |
| **`go:generate` генератор декодера** | М1 | Генерация диспетчера опкодов из CSV/JSON; используется в М3 и далее |
| **Самописный дизассемблер** | М3 | Дизассемблер для 8080 и 6502; основа создания собственных тест-ROM |
| **Дифференциальный трейсер** | М3 | Сравнение трейсов с golden traces (Mesen, BlastEm); используется в М3 и далее |
| **Инженерный дневник** | М4 | Markdown-дневник решений, тупиков, гипотез — в репозитории, ведётся до М18 |
| **ADR-документ** | М4 | Architecture Decision Record на каждое ключевое архитектурное решение |
| **Ebitengine/SDL2 вывод** | М5 | Минимальная графическая оболочка; только граница вывода готового фреймбуфера |
| **TUI-отладчик (Bubble Tea)** | М6 | Дизассемблер, step/step-over, брейкпоинты, дамп памяти/регистров в реальном времени |
| **Savestates и Rewind** | М6 | Сохранение/восстановление полного состояния эмулятора; основа детерминизма |
| **«Сломанный эмулятор» (первый кейс)** | М7 | Atari 2600: 90% тестов → локализация → гипотеза → фикс → регрессионный тест |
| **WASM-экспорт** | М10 | Экспорт CHIP‑8 или NES в WebAssembly; интерактивный эмулятор в браузере |
| **Netlist-симуляция 6502** | М12 | Транзисторная модель по Visual6502; понимание уровня «real hardware» |

## 4. Архитектура модуля (стандартный шаблон)

### 4.1 Семиглавная структура каждого модуля

Каждый модуль курса состоит из **семи стандартных глав**. Единообразие шаблона обязательно —
это главное средство борьбы с расползанием масштаба:

| Глава | Название | Содержание |
|---|---|---|
| **0** | Подготовка | Контекст, обзор существующих эмуляторов, поиск и чтение документации, настройка среды, репозиторий, CI, тест-пайплайн |
| **1** | CPU | Теория → архитектурное проектирование (ADR) → пошаговая практика |
| **2** | Память и шины | MMIO, bank switching, зеркалирование, арбитраж |
| **3** | Графика | Видеочип, тайлы, спрайты, синхронизация с CPU |
| **4** | Звук | APU/PSG/FM, синтез, буферизация |
| **5** | Ввод/вывод | Контроллеры, периферия, форматы носителей |
| **6** | Интеграция | Связывание компонентов, запуск реальных ROM, отладка, профилирование |
| **7** | Что дальше | Cycle-accuracy, savestates, netplay, TAS, ссылки, следующий модуль |

### 4.2 Шаблон блока «Подготовка» (Глава 0)

Каждый модуль начинается с обязательного блока:

- Где брать даташиты, схемы, таблицы опкодов (Archive.org, официальные репозитории, nocash).
- Как читать принципиальные схемы (подтягивающие резисторы, open bus, фронт/спад CLK-сигнала).
- Настройка тулинга: Delve (отладчик), `pprof` (профайлер), `go vet`, `golangci-lint`.
- Обзор существующих эмуляторов данной системы: что читать, чему учиться.
- Работа с тест-сьютами: Klaus Dormann, blargg, Mooneye, Tom Harte.
- Подключение дифференциального трейсера (спутник из М3) к новой системе.

### 4.3 Шаблон урока внутри главы

Каждый урок строится по единой четырёхчастной структуре:

```
┌─────────────────────────────────────────────────────┐
│  1. ИСТОРИЧЕСКИЙ И АППАРАТНЫЙ КОНТЕКСТ               │
│     Логика инженеров эпохи, чтение оригинального     │
│     даташита и электрической схемы.                  │
├─────────────────────────────────────────────────────┤
│  2. ИНЖЕНЕРНОЕ ПРОЕКТИРОВАНИЕ (Design Choices / ADR) │
│     Контекст → ≥3 альтернативы (включая             │
│     соблазнительную, но ошибочную) → критерии        │
│     выбора → «когда решение сломается» → тесты.      │
├─────────────────────────────────────────────────────┤
│  3. ПОШАГОВАЯ РЕАЛИЗАЦИЯ НА GO                       │
│     Итерация 1 (v0): наивная → тесты валятся         │
│     Итерация 2 (v1): исправление логики              │
│     Итерация 3 (v2): рефакторинг и интеграция        │
├─────────────────────────────────────────────────────┤
│  4. ТЕСТИРОВАНИЕ И ВАЛИДАЦИЯ                         │
│     Юнит-тесты (testing.T).                          │
│     Прогон верификационных тест-ROM.                 │
│     Сравнение с эталонными трейсами (трейсер из М3). │
└─────────────────────────────────────────────────────┘
```

### 4.4 Трёхуровневая модель объяснения

Каждая техническая тема раскрывается на трёх уровнях:

| Уровень | Название | Что объясняется |
|---|---|---|
| **1** | Conceptual | Физический и архитектурный смысл: зачем это существует |
| **2** | Engineering | Представление и моделирование в коде на Go |
| **3** | Real Hardware | Пограничные случаи, артефакты, баги кремния, ревизии чипов |

## 5. Специальные форматы уроков и рубрики

### 5.1 Форматы специализированных уроков

Помимо стандартного урока, в курсе применяются специальные форматы:

| Формат | Назначение |
|---|---|
| **Investigation** | Исследование неизвестного поведения железа: гипотеза → эксперимент → вывод. Первый раз — в модуле HLE vs. LLE |
| **Debugging** | Поиск и локализация багов в реальном эмуляторе |
| **Reverse Engineering** | Анализ расхождения поведения железа с даташитом |
| **Performance** | Профилирование, поиск узких мест, разгон FPS |
| **Testing** | Доказательство корректности: тест-сьюты, fuzzing, golden traces |
| **Documentation Archaeology** | Сличение противоречивых источников; анализ исходников MAME. Первый раз — в MODULE «Схемотехника и реверс-инжиниринг» |

### 5.2 Рубрика «Сломанные эмуляторы» (Broken Emulators)

Ключевой дидактический приём, впервые применяемый в **М7 (Atari 2600)**: студент получает
эмулятор, проходящий ~90% тестов. Задача — **выдвинуть гипотезы, локализовать баги, написать
регрессионные тесты и починить**.

Это приучает к реальному рабочему процессу: ни один эмулятор не пишется сразу правильно.
Формат повторяется в каждом последующем сложном модуле.

### 5.3 Рубрика «Музей багов»

Формат разбора реальных ошибок при разработке, встроенный в Главу 6 (Интеграция) каждого модуля:

```
Симптом → Гипотеза → Процесс поиска → Фикс → Регрессионный тест
```

Источники: врезки с разбором эталонных эмуляторов (Mesen, Stella, BlastEm, DuckStation,
SameBoy, RPCS3).

### 5.4 Рубрика ADR (Architecture Decision Record)

Все ключевые архитектурные решения оформляются в виде ADR — начиная с **М4 (Apple I)** как первого
полноценного случая:

```
Контекст:          [ситуация и проблема]
Альтернативы:      [≥3 варианта, включая соблазнительный неправильный]
Критерии выбора:   [производительность / точность / сложность / Go-специфика]
Решение:           [выбранный вариант с обоснованием]
Последствия:       [когда решение сломается; как откатить]
Верификация:       [тесты, подтверждающие правильность]
```

## 6. Промежуточные лабораторные модули (Labs)

Между системными модулями внедряются **изолированные концептуальные Lab-модули** — они вводят
необходимые концепции до того, как те встречаются в системном контексте. Являются обязательной
частью основной линейки.

| Lab | Место | Ключевые темы |
|---|---|---|
| **Memory Lab** | М1 → М2 | Байтовая/словная адресация, endianness, MMIO, bank switching, зеркалирование, open bus, write-only регистры, побочные эффекты чтения |
| **CPU Lab** | М2 → М3 | Аккумуляторная/стековая/регистровая архитектуры; микрокод; интерпретаторы (switch, func-table); флаги ALU |
| **Bus Lab** | М4 → М5 | Общая шина; арбитраж между CPU, RAM, ROM, таймером, UART, видео; wait states |
| **Interrupt Lab** | М5 → М6 | IRQ, NMI, маскирование, контроллер прерываний (PIC), вложенные прерывания, приоритеты, латентность |
| **Timing Lab** | М6 → М7 | Счётчики циклов, master clock, делители частоты, event scheduler, сканлайн-планировщик, cycle-accurate эмуляция |
| **DMA Lab** | М7 → М8 | Процессорное копирование → выделенный DMA-контроллер → конкуренция CPU и DMA за шину (steal cycles) |

## 8. Уровни точности эмуляции

Курс явно и систематически разграничивает уровни точности, объясняя компромиссы:

```
Frame-accurate
    │   Состояние обновляется раз в кадр (~60 Гц).
    │   Самый быстрый, самый неточный.
    │   Подходит для простых систем с фреймбуфером.
    ▼
Scanline-accurate
    │   Состояние обновляется раз в строку развёртки.
    │   Практический компромисс для большинства 8-/16-битных систем.
    │   Достаточен для NES, Mega Drive.
    ▼
Cycle-accurate
        Состояние обновляется каждый такт мастер-клока.
        Необходим для Atari 2600, SNES-спецэффектов, Amiga Copper.
        Детерминизм → savestates, rewind, TAS, netplay.
```

**Master clock и делители частоты** — базовый паттерн всего курса, впервые вводится в Timing Lab
и описывается в Главе 0 каждой системы:

```
MASTER CLOCK
    ├── ÷ 3  → CPU (∼1 МГц)
    ├── ÷ 1  → PPU (∼3 МГц)
    └── ÷ 6  → APU (∼0.5 МГц)
```

Детерминизм однопоточного ядра эмулятора — это не ограничение, а **ценное свойство**:
он является необходимым условием для savestates, rewind, TAS и netplay.

## 9. Тестовая культура

### 9.1 Test-Driven Development как основа

Тестирование встроено в каждый модуль, а не добавляется после. Принцип: **«красный → зелёный →
рефакторинг»** применяется к каждой реализуемой функции эмулятора. CI запускает все тесты
автоматически при каждом изменении кода.

### 9.2 Канонические тест-сьюты по платформам

| Платформа | Тест-сьюты |

| Intel 8080 | Klaus Dormann CPU exerciser, 8080PRE |
| MOS 6502 / NES | Tom Harte 6502 tests (65536 тестов/опкод), Klaus Dormann, nestest, blargg |
| Zilog Z80 | ZEXALL, ZEXDOC |
| Apple II | A2 diagnostics ROMs |
| ZX Spectrum | FUSE CPU tests |

### 9.3 Три уровня верификации

Каждое утверждение о поведении железа проходит через три уровня:

```
✅ «Проверено тестом»        — автоматизированный тест проходит на реальном
                               железе или эталонном эмуляторе
📄 «Из документации»        — прямая цитата из официального даташита или
                               технического руководства
💬 «Наблюдение сообщества»  — задокументированное наблюдение из Nesdev Wiki,
                               nocash, gbdev.io и т.п.
```

### 9.4 Инструменты верификации

- **Дифференциальное тестирование** (спутник М3): сравнение трейсов собственного эмулятора
  с golden traces Mesen, BlastEm, DuckStation — применяется во всех модулях начиная с М3.
- **Самописные тест-ROM** (спутник М3): ассемблирование собственным ассемблером → загрузка →
  снятие трейсов.
- **Fuzzing:** `testing.F` для поиска краевых случаев в декодере опкодов.

## 10. Встроенные инструменты разработки

### 10.1 Отладчик — создаётся в М0, растёт до М18

Отладчик — **первый практический результат курса**, создаётся в М0 как headless-инструмент
и развивается вместе с каждым последующим модулем:

| Этап | Что добавляется |
|---|---|
| **М0** | Дамп регистров, дамп памяти (hex+ASCII), трейс инструкций |
| **М3** | Дизассемблер для 8080 и 6502; базовый трейсер |
| **М6** | TUI-оболочка (Bubble Tea): step/step-over, брейкпоинты, живой дамп |
| **М6** | Savestates и rewind |
| **М10** | WASM-экспорт отладчика в браузер |
| **М12+** | Поддержка 32-битных ISA (MIPS, ARM); расширение для GPU-состояния |

### 10.2 Принцип «UI последним»

Архитектура ядра эмулятора **запускается в headless/CLI-режиме** с первой практики. Графические
интерфейсы и оконные библиотеки не вводятся до тех пор, пока CPU и шина не работают корректно
(М5). Графический вывод — только через готовый фреймбуфер в Ebitengine или SDL2. Ядро при этом
остаётся полностью независимым от графической библиотеки.

## 11. Исследовательская деятельность и реверс-инжиниринг

### 11.1 Работа в условиях неполной документации

Специальный блок MODULE «Схемотехника и реверс-инжиниринг» (между М8 и М9) посвящён тому,
**«как узнать работу неизвестной системы»**:

- Анализ исходников MAME/MESS — без страха читать чужой код.
- Чтение патентов (IBM, Motorola, Intel) как источника технической документации.
- Дизассемблирование ROM и прошивок (используется дизассемблер из спутника М3).
- Создание тест-ROM вручную: ассемблирование → загрузка → снятие трейсов.
- Сравнение поведения с несколькими независимыми источниками.
- Формат «Documentation Archaeology»: сличение противоречивых источников.

### 11.2 Чтение принципиальных схем

Базовые навыки схемотехники закладываются в **М0** и расширяются в MODULE
«Схемотехника и реверс-инжиниринг»:

- Подтягивающие / стягивающие резисторы и их роль в open-bus поведении.
- Срабатывание триггеров по фронту / спаду CLK-сигнала.
- Дешифрация адресов: как ROM и RAM делят адресное пространство.
- Чтение timing diagrams из даташитов.

### 11.3 Юридическая безопасность

- Использование только homebrew, тестовых ROM и Public Domain контента.
- Запрет на распространение проприетарных BIOS в рамках учебника.
- Свободное ПО: FreeDOS, Unix V6 (под лицензией Caldera), CP/M, EmuTOS.
- Разбор прецедента *Sony v. Connectix (2000)*: чистый реверс-инжиниринг через анализ
  внешнего поведения без копирования кода — законен.

## 13. Управление рисками проекта

### 13.1 Главные риски

| Риск | Описание | Нейтрализация |
|---|---|---|
| **Расползание масштаба** | 5 000 страниц рискуют превратиться в 50 000 | Жёсткий 7-главный шаблон модуля; единый глоссарий; граф зависимостей; строгая архитектурная преемственность кода |
| **Тихие фактические ошибки** | Галлюцинации LLM в адресах регистров, битах флагов, тактах инструкций | Три уровня верификации; привязка каждого утверждения к машиночитаемым тестам и первоисточникам |
| **Устаревание** | Версии библиотек и инструментов меняются | Фиксация принципов и архитектурных паттернов, а не конкретных версий |
| **Дефицит документации** | Сложные и экзотические системы плохо задокументированы | MODULE «Схемотехника и реверс-инжиниринг»; анализ MAME; тесты на реальном железе; патенты |
| **Распад инструментальной базы** | Спутники написаны разрозненно и несовместимы | Спутники встроены в основную линейку с первого модуля; все используют общий фреймворк Bus/CPU/Clock |

### 13.2 Структурные меры защиты

- **Граф зависимостей модулей** — явная карта: какой модуль от чего зависит.
- **Единый глоссарий** — термины определяются один раз и используются консистентно.
- **CI-конвейер** — тесты запускаются автоматически при каждом изменении кода.
- **Вертикальный срез первым** — перед масштабированием: отшлифовать шаблон на М0 + CHIP‑8 +
  6502, прежде чем тиражировать структуру.
- **Общий инструментальный фреймворк** — спутники не создаются с нуля в каждом модуле; они
  наращиваются от М0 на общей кодовой базе.
